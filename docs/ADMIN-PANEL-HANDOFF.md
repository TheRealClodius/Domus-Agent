# Frontend: Agent Admin Panel

## What this is

A handoff doc for the Domus frontend agent. Two new read-only API endpoints were
added to the **domus-agent** service (Railway). This doc describes what they return,
how to call them, and what the frontend should build to consume them.

---

## What was built on the backend (domus-agent)

Two new GET endpoints in `main.py`, both protected by `Authorization: Bearer <DOMUS_SERVICE_TOKEN>`:

### `GET /admin/domus-context?space_id=X&user_id=Y`

Snapshots the Domus agent's assembled context for a given space. Runs all 7 context
fetchers in parallel (same ones used to build the live system prompt) plus 4 health
count queries. Clears the in-process entity index cache on entry so the response

## How to call from the frontend

The service token must stay server-side. The pattern is the same as the existing
SSE proxy in Vercel:

1. Add two Next.js API routes (e.g. `app/api/admin/domus-context/route.ts` and
   `app/api/admin/builder-context/route.ts`)
2. Each route validates the user session (Supabase auth), then forwards to the
   agent service with `Authorization: Bearer ${process.env.DOMUS_SERVICE_TOKEN}`
3. The frontend UI calls these Next.js routes — never the agent service directly

Agent service base URL: `process.env.AGENT_SERVICE_URL` (already used for SSE proxy).

## What to build in the UI (broad strokes)

A single admin/debug panel, likely at `/admin` or accessible from the settings
sidebar. Gated to authenticated users (admin-only role check if the product has one,
otherwise just authenticated).

### Domus Agent section

Fetch `/api/admin/domus-context?space_id=<current>&user_id=<current>`.

**Health bar / status card:**
- Turn count vs threshold (`active_turn_count / compaction_threshold`) — progress bar or fraction
- `compaction_needed: true` → amber warning
- Fact count, edge count, summary count — three small stat chips
- `assembled_at` timestamp

**Prompt structure:**
- Total token estimate + model name (from `prompt_structure`)
- Three rows (Static / Semi-static / Dynamic) showing token estimates and cached status
- Char counts for the two static subsections (base instructions, iframe builder context) — found in `blocks.static.sections`

**Entity index:**
- Total entity count + breakdown by type (small tag list or table)
- `recently_active` list (3 items max)

**Memory:**
- User facts list (content + confidence)
- Conversation summaries (collapsed by default)
- Recent turns (last 5, role-labelled)

### Builder Agent section

Fetch `/api/admin/builder-context?space_id=<current>&user_id=<current>`.

**Prompt structure:**
- Total token estimate
- Section breakdown (role/catalog/dsl/examples/design) — bar chart or table
- Model name

**App inventory:**
- Two lists: "Declarative apps" and "Iframe apps"
- Each entry: name, component/action count (declarative), building/error status, updated_at
- Link out to the entity on canvas if possible

---

## Key design notes for the frontend agent

- This is a **dev/debug panel**, not a user-facing feature. Keep it functional over
  beautiful — monospace where appropriate, dense information layout.
- Data is fetched on page load and has a manual refresh button. No polling needed.
- The `dynamic.note` field explains why dynamic token estimate shows 0 — surface this
  as an info tooltip rather than leaving it looking broken.
- `compaction_needed: true` is the most actionable signal. Make it visually prominent.
- The two fetches (`domus-context` and `builder-context`) are independent — fetch in
  parallel, render each section as it arrives.

## Not in scope

- Writing back to the agent (this is read-only observability)
- Compaction trigger button (could be a follow-up)
- Per-entity deep-dive from the admin panel
- Any changes to the agent service itself
